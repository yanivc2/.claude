# AP Control — בקרת ספקים, חשבוניות ותשלומים

שכבת בקרה על הזרימה **ספק → חשבונית → צ׳ק** לרשת קמעונאית (סופרמרקטים 24/7).
מטרות: מניעת כפילויות תשלום, מניעת תשלום לא מאושר, מעקב פירעון צ׳קים, ותחליף לדוחות
Excel ידניים. **זו בקרת תשלומים (Accounts Payable) — לא מערכת הנהלת חשבונות ולא דיווח מע"מ.**

המפרט המלא: [`PROJECT_BRIEF.md`](./PROJECT_BRIEF.md).

## מה נבנה (שלבים 1, 1b, 2, 3)

מומשו שלב 1 (ליבה), 1b (תמונות), 2 (התאמת בנק) ו-3 (OCR) מתוך תוכנית השלבים (§8 במפרט):

- **מודל נתונים מלא** (SQLite) + seed של 3 חברות / 4 חנויות / 4 חשבונות בנק (1:1) + 2 תפקידים.
- **שער אישור ספק** — פעולת בעלים בלבד (R6). ספק חדש נפתח כ-`pending` וניתן להזין חשבוניות מיד, אך תשלום חסום עד אישור.
- **הזנת חשבוניות ידנית** עם אכיפת חוקי הבקרה:
  - **R2** — זיהוי כפילות: מספר הקצאה (מפתח חזק, חסימה קשה) → ספק+מספר חשבונית (אזהרה רכה).
  - **R3** — חשבונית מס מעל 5,000 ₪ לפני מע"מ ללא מספר הקצאה → חסימה רכה (`on_hold`) עד השלמת הקצאה או עקיפת בעלים.
  - **R4** — אותו ספק + אותו סכום בחלון תאריכים → אזהרה רכה, נדחית עם סיבה.
- **תשלומים (צ׳קים)** עם אכיפת:
  - **חסימת צ׳ק** — אין הנפקה ללא מספר צ׳ק **וגם** חשבונית מקושרת.
  - **R1** — כל החשבוניות המקושרות ב-`approved_for_payment` **וגם** הספק `approved`.
  - **R5** — סכום הצ׳ק = סכום שורות התשלום (חשבוניות פחות זיכויים).
- **זיכויים** — `doc_type=credit_note`, נשמרים כסכום שלילי, פטורים ממספר הקצאה.
- **דוחות (שלושת דוחות §7)** — "צ׳קים בחוץ" (התחייבות חיה פר חשבון), "בדיקת חשבונית" (חיפוש
  לפי מספר/הקצאה/ספק), ו-"רווחיות" (פר חנות בתקופה: קניות אוטומטיות מהחשבוניות מול מכירות Z
  ידניות → רווח גולמי ואחוז רווח).
- **פירעון ידני** של צ׳קים (שלב 1), **יומן ביקורת** מלא לכל פעולה משנת-מצב.

### שלב 1b — תמונות (מומש)

- צירוף סריקה/צילום לחשבונית (JPG/PNG/WEBP/GIF/PDF, עד 10MB) בעת ההזנה או מאוחר יותר.
- הקבצים נשמרים תחת `uploads/` (מחוץ ל-git) בשם UUID לא-ניחוש; רק שם הקובץ נשמר ב-`invoices.image_path`.
- הצגה/פתיחה של התמונה במסך החשבונית; החלפה מוחקת את הקובץ הקודם. **ללא OCR** (זה שלב 3).

### שלב 2 — התאמת בנק (מומש)

- **מנוע R7:** התאמת תנועת חובה מהבנק לצ׳ק פתוח לפי **סכום + חלון תאריך פירעון + כיוון חובה**
  (ללא תלות במספר הצ'ק — §11.1). התאמה חד-משמעית → פירעון אוטומטי; שני צ'קים באותו סכום+חלון
  → **סימון למזכירה להכריע**; מספר צ'ק שמופיע בתיאור התנועה → **התאמה דטרמיניסטית** (בונוס).
- **קליטת תנועות** בשלושה נתיבים: ייבוא CSV, הזנה ידנית, או scraper (ראה למטה).
  ייבוא אידמפוטנטי — טווח חופף לא יוצר כפילויות.
- **מסך התאמת בנק:** תנועות לא מותאמות עם הצעות התאמה, כפתור "התאמה אוטומטית", הכרעה ידנית,
  וביטול התאמה. פירעון מעדכן אוטומטית את דוח "צ׳קים בחוץ".
- **scraper (israeli-bank-scrapers)** — **תלות אופציונלית** בטעינה עצלה. הרץ `npm run scrape`
  לאחר התקנתה והגדרת ה-credentials. **🔴 טעון אימות מול חשבון אמיתי** (§11.1 מספר צ'ק, §11.2
  2FA) לפני הסתמכות בפרודקשן — מנוע ההתאמה עצמו עובד ללא תלות באימותים אלה.

### שלב 3 — OCR (מומש)

- **קריאה מהתמונה והשוואה למוקלד** (§3/§8): מריצים OCR על תמונת החשבונית, המערכת מחלצת
  שדות מועמדים (מספר הקצאה, מספר חשבונית, תאריך, סכומים) **ומשווה למה שהוקלד** — מסמנת
  תואם / אי-התאמה / OCR לא זיהה / רק ב-OCR. פיצ'ר בקרה: תופס טעויות הקלדה ואי-התאמות.
- **OCR לעולם אינו דורס** נתונים שהוזנו — הוא נשמר בנפרד (טבלת `invoice_ocr`) ומוצג להשוואה.
  ניתן להחיל מספר הקצאה שזוהה על חשבונית שחסר בה.
- **מקומי בלבד** (§12 — מסמכים לא יוצאים מה-PC): `tesseract.js` כ**תלות אופציונלית בטעינה
  עצלה**; ספק ה-OCR מופשט ומוזרק (ניתן להחליף בעתיד). שכבת חילוץ השדות טהורה ונבדקת ללא מנוע.
  🔴 דיוק OCR בעברית על חשבוניות אמיתיות מוגבל — כל תוצאה היא הצעה לאימוש אנושי, לא סמכות.

### מה עדיין לא (שלבים עתידיים, מתועד במפרט)

4 — הדפסת צ׳קים (תקן 501/MICR, טעון אישור בנק 🔴).

## הרצה

```bash
cd ap-control
npm install
cp .env.example .env      # ערוך PORT / DB_PATH לפי הצורך
npm start                 # http://localhost:3000
```

- `npm test` — מריץ את חבילת הבדיקות (חוקי הבקרה, כספים, CSV, מנוע R7).
- `npm run reset-db` — מוחק ובונה מחדש את בסיס הנתונים עם seed (זהירות: מוחק נתונים).
- `npm run seed` — seed אידמפוטנטי (בטוח להרצה חוזרת; לא דורס נתונים קיימים).
- `npm run scrape [YYYY-MM-DD]` — שלב 2: מושך תנועות מהפועלים ומייבא (דורש
  `npm install israeli-bank-scrapers` + credentials ב-env). ראה `.env.example`.

## החלטות תכנון (למי שממשיך)

- **כספים כ-agorot שלמים** (`INTEGER`) בכל שכבת הדומיין — נמנע מ-drift של נקודה צפה,
  קריטי במיוחד ל-R5. המרה לשקלים רק בגבול ה-UI (`src/lib/money.js`).
- **שכבות:** `routes` (דק) → `services` (חוקי הבקרה) → `db`. כל פונקציית service מקבלת
  `db` אופציונלי כדי לאפשר בדיקות מול DB in-memory.
- **תפקיד פעיל (owner/secretary)** נשמר ב-cookie פשוט ומוחלף מראש העמוד. **זו הקלה של
  שלב 1, לא גבול אבטחה** — המערכת רצה מקומית והמזכירה עובדת לבד (§9). הוספת אימות אמיתי
  היא שדרוג עתידי אם המערכת תיחשף מעבר לרשת המשרד.
- **אישור חשבונית לתשלום** זמין לשני התפקידים, אך שחרור חשבונית `on_hold` (R3/החזקה) ואישור
  ספק — בעלים בלבד (R6). זו פרשנות תפעולית של המפרט; ניתן להדק בהמשך.
- **צ׳ק אחד = חשבון בנק אחד:** כל החשבוניות בצ׳ק חייבות להשתייך לאותו חשבון (מיפוי חנות↔חשבון 1:1).
- **יישום מלא בלבד** בשלב 1 (אין תשלום חלקי של חשבונית) — פישוט מודע, מרחיב בעתיד.

## סוגיות פתוחות (מהמפרט §11 — טעונות אישור/אימות)

- ✅ מספרי ח.פ. של 3 החברות — הושלמו ב-seed (יניב רום 515325405, על הדרך 514737832, פינק מרקט 516632627). ה-seed גם משלים ח.פ. חסר במסד קיים בלי לדרוס ערך ידני.
- 🔴 מספר צ׳ק בנתוני ה-scraper (§11.1), 2FA בהפועלים (§11.2) — **עדיין טעוני אימות מול חשבון
  אמיתי** לפני הפעלת ה-scraper בפרודקשן. מנוע ההתאמה (R7) כבר עובד ונבדק ללא תלות בהם; מספר צ'ק
  זמין רק משדרג את ההתאמה לדטרמיניסטית. עד לאימות — נתיבי CSV/ידני זמינים ומלאים.
- ספי מספר הקצאה (5,000 ₪) וחלון הכפילות (30 יום) ניתנים לכוונון ב-`src/config.js` / env.

## הערת אבטחה — תלויות

`npm audit` נקי — **0 פגיעויות**. שרשרת ה-build של `ejs@3` (שגררה DoS ב-`brace-expansion`)
נסגרה בשדרוג ל-`ejs@6`. התבניות אומתו לאחר השדרוג: כל 15 מסלולי התצוגה מרונדרים תקין,
כולל re-render של אזהרות והצגת תמונה. הרצה חוזרת של `npm audit` מומלצת מעת לעת.

## גיבוי (חובה — §12)

קובץ ה-SQLite (`data/`) ותיקיית התמונות (שלב 1b) הם נקודת כשל יחידה. הגדר **גיבוי יומי
אוטומטי מחוץ ל-PC**. הקבצים תחת `data/` אינם נכללים ב-git (ראה `.gitignore`).
